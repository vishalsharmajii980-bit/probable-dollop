## Problem 1: `titan-links.com` stuck ("✖ Stuck on https://titan-links.com/vKRz7a1")
Root cause: titan-links.com hard-blocks hosting/datacenter IPs with
HTTP 403 "Access Blocked — Hosting / Data Center connection detected" on `/ALIAS`.
The old code had no titan handler at all, so the generic loop timed out at 100s+.

Fixes:
- `g2s/engine.py`
  - `FORCE_TUNNEL_HOSTS = {"titan-links.com", "www.titan-links.com"}` + `DATACENTER_GATE_RE`.
  - `_tick`: detects the "Access Blocked / data center / hosting" gate page in `snap["text"]`
    and raises `BypassError` containing "blocked" + "data center" → the existing
    direct→residential-tunnel auto-failover in `_resolve_on_worker` fires automatically.
  - `_try_titan_links_direct`: new dedicated LinkShort solver (alpha-links family):
    `GET /ALIAS` → interstitial counter → `form#go-link` → wait `counter_value`s →
    `POST /links/go` with `X-CSRF-Token` + `_csrfToken` + `ad_form_data` → JSON `url`.
    Uses `_aiohttp_req_kwargs()` so it works through the tunnel proxy (request-level args).
  - `_resolve_on_worker`: when a residential tunnel proxy is active, the titan direct
    solver is tried through the tunnel BEFORE opening the browser.
  - Browser path: `titan-links.com` added to the 6s final-page timer wait list;
    `/links/go` JSON responses are captured in `_attach.on_response` → `set_result`.
  - titan-links.com added to `no_accel_hosts` and `_dedicated_shorteners`.
- `g2s/db.py`
  - `DEFAULT_SHORTENERS` += titan-links.com (shows in Admin Panel tunnel list).
  - `should_use_tunnel_for_url()` returns `True` for titan-links.com → always routed via
    the connected Android/PC tunnel device, no manual toggle needed.

Live test (from a datacenter sandbox IP, where the 403 gate is expected):

## Problem 2: `vipshort.in` / `link.vipshort.in` stuck on blog.hindumantra.net
Root causes found by live browser probing:
- The `m.vipshort.in/<alias>?slt=…` final link is SINGLE-USE and Referer-bound. The old code
  fetched it with `ctx.request` (API GET) → always bounced to `link.vipshort.in` ("no go-link
  form yet — continuing hops" → stuck).
- The legacy `vip1=4` POST poisons the WP-safelink (`wpsl_token`) session server-side on
  non-geniousguide blogs (e.g. blog.hindumantra.net), invalidating every later slt token.
- Hop cap of 8 was too low; the real chain needs ~14 hops before a valid slt appears.

Fixes (`g2s/engine.py`):
- wpLinks shortcut: the slt link is now opened with a REAL browser navigation
  (`page.goto(slt, referer=<blog page>)`); the `m.vipshort.in` handler then polls for
  `form#go-link` (injected after the on-page counter), submits it via fetch with CSRF,
  falls back to clicking the site's own "Get Link" button + native form submit, and the
  `/links/go` JSON response is also captured globally in `on_response`.
- Bounce recovery: if we land back on `link.vipshort.in` after hops started, re-enter the
  chain via `https://<blog>?go=<alias>` instead of getting stuck.
- Hop cap 8 → 14 (log shows "hop N/14"); blog host is remembered in `job.vipshort_blog_host`.
- `vip1=4` legacy POST is now only sent on the original `geniousguide.com` deployment,
  never mid-hop and never on other safelink blogs.
- `_try_vipshort_direct` (aiohttp): hands off to the browser worker when the safelink blog
  is not geniousguide.com; referer for the m.vipshort fetch now uses the real blog host.
